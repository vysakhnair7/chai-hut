# Frontend ↔ Backend API mapping

Derived from the backend source (`app/routers/*`, `app/schemas/*`, `app/core/rbac.py`), not from
assumptions. Live docs: `GET {API}/docs`. All amounts are **strings** in JSON (e.g. `"42.00"`);
the frontend only formats them, it never computes with them. Errors are always
`{"error": {"code", "message", "details?"}}`. Lists are `{items, total, limit, offset}` (`limit` ≤ 200).

Roles: **O** owner · **M** manager · **C** cashier.

## Authentication

| Feature | Endpoint | Request | Response | Roles |
|---|---|---|---|---|
| Login | `POST /auth/login` | `{username, password}` | `{access_token, token_type, expires_in}` | public |
| Current user | `GET /auth/me` | – | `{id, username, full_name, role, status, created_at}` | all |
| Change own password | `POST /auth/change-password` | `{current_password, new_password}` | `{detail}` | all |

Bearer JWT in the `Authorization` header. No cookies, no refresh token (60-minute access token).

## Discrepancies and missing backend functionality

The backend contract wins. Nothing below was faked in the UI and the backend was not changed.

| # | Spec asks for | Backend reality | Frontend behaviour |
|---|---|---|---|
| 1 | Customer **email** | No such field | Not shown |
| 2 | Order **special instructions** | No field on orders/items | Not shown |
| 3 | Order summary with GST/discount/total **before** submit | No quote/preview endpoint | The cart shows quantity × unit price only, labelled as an estimate; GST, discount and the real total appear on the confirmation, from the server's response. *Suggested addition:* `POST /orders/preview` |
| 4 | **Invoice listing** | No list endpoint (only per-order `/bill`) | Invoices are reached from Orders / Payments (order → bill) |
| 5 | **Payment-method distribution** chart | No aggregate endpoint (summing `/payments` in React would duplicate backend logic) | Not drawn. The dashboard shows collected vs credit vs outstanding from the financial report instead. *Suggested:* a `by_method` block in `/reports/financial` |
| 6 | **Gross / net profit trend** charts, **revenue vs expenses** over time | `/reports/financial` is one summary per range; `daily[]` has sales only | Profit and revenue-vs-expenses are shown for the selected range, not as a time series. *Suggested:* daily COGS/expenses in `daily[]` |
| 7 | **Customer purchase trends** | Only per-company (`/reports/corporate`) | Company-level table/chart |
| 8 | **HTTP-only cookie** session / refresh token | Bearer token in the response body only | Token kept in `sessionStorage` (cleared when the tab closes, never `localStorage`); on 401 the user is signed out |
| 9 | Manager can add products and manage categories | Backend limits this to the owner; managers may change **price and stock** | Manager sees price/stock editing only |
| 10 | **Settings** page | No settings API; only change-password exists | Settings = profile + change password |
| 11 | Orders **date range** filter | `business_date` is a single day | Single-date filter |
| 12 | Duplicate-safe **order** retries | No idempotency on `POST /orders` | Submit is disabled while pending; on a network failure the cart is kept and the user is told to check Active Orders before retrying. Payments/settlements *are* idempotent and send an `Idempotency-Key` |
| 13 | Unpaid-orders filter / payment state in order list | Not in the list response | Payment state is shown in the order detail (bill) |
| 14 | Cashier "frequently ordered" for a walk-in | Only per registered customer | Shown for registered customers; popular products shown in the menu otherwise |
| 15 | CORS | Allowed origins come from the backend's `CORS_ORIGINS` env | Set `CORS_ORIGINS=http://localhost:5173` for local dev (no backend code change) |
